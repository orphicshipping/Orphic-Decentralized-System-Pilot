# Retained calibration and history inspection

These read-only inspection APIs keep certificate parsing, declared applicability,
issuer authenticity, correction authority and physical qualification separate.
They consume existing Link and NCP records and never register a calibration,
change a grant, interpret a new hardware protocol or rerun a job.

## Certificate profile

`ciw.calibration_inspection.inspect_certificate(raw)` implements
`ncp.dcc-3.3.0-scalar-inspection.v1`. It accepts at most 1 MiB of UTF-8 XML with the
PTB DCC namespace `https://ptb.de/dcc` and exact declared version `3.3.0`.
DTD/entity declarations, non-UTF-8 encodings, excessive depth/element counts,
duplicate XML IDs and unresolved `refId` references are refused. The reader
never fetches an XML schema, external entity, attachment or certificate URL.

The bounded profile extracts the certificate identifier, top-level calibration
item identification values, calibration performance/issue dates and scalar
`dcc:quantity/si:real` values and units. It preserves decimal spelling such as
`1.200`. Unsupported quantity encodings are counted rather than converted.
Calibration points do not establish a valid operating range; performance dates
do not establish a recalibration interval. This implementation follows the
[PTB DCC 3.3.0 schema documentation](https://www.ptb.de/dcc/v3.3.0/autogenerated-docs/dcc_xsd.html)
for these selected fields. It does **not** perform full XSD validation or
cryptographic signature/issuer verification. `INSPECTION_PROFILE_PASSED` means
only that these explicitly selected structural checks passed.

```powershell
python -m ciw.calibration_inspection certificate.xml --output retained-inspection
```

The new directory retains `certificate.xml` byte-for-byte and `inspection.json`
with its hash, byte count, profile/version, facts and separate statuses. Existing
output directories are refused. Exit 0 means the inspection profile passed;
it does not mean an approved calibration or authenticated certificate.

### Existing Link calibration declarations

`inspect_link_calibration(declaration, device=device, observation=observation,
scope=scope)` first validates the existing `ciw.link-calibration-declaration.v1`,
manifest and observation. The declaration's embedded certificate limit remains
32 KiB. It checks the observation's exact calibration reference, manifest,
channel, unit and declared half-open validity interval. Unknown acquisition time
stays unknown; host receipt time is not substituted.

An optional `ncp.dcc-link-scalar-scope.v1` supplies explicit **operator
interpretation**, bound to the exact certificate bytes:

```json
{
  "schema": "ncp.dcc-link-scalar-scope.v1",
  "certificate_ref": "sha256:<64 hexadecimal digits>",
  "item_xml_id": "certificate-item-id",
  "identification_issuer": "manufacturer",
  "quantity_xml_id": "certificate-scalar-quantity-id",
  "channel_id": "CH0",
  "certificate_unit": "\\milli\\metre",
  "link_unit": "mm",
  "range": {"minimum": "0.00", "maximum": "25.00"},
  "interpretation_basis": "Explicit operator review reference and interpretation"
}
```

The selected item's identification must match the Link instrument identity under
the chosen identification issuer. The quantity and exact certificate unit token
must exist, and the quantity must explicitly reference the selected item through
`refId`. A reference to another item is a mismatch; absent association stays
unknown rather than being inferred from document proximity. The operator's channel and unit mapping must match the Link channel;
this does not authenticate that mapping or perform a conversion. The inclusive
range is an operator declaration, never inferred from certificate point extrema.
For an existing native reported scalar, the original decimal spelling is used
at the range boundary. Opaque undecoded GaugeLink observations retain unknown
range applicability; this inspector does not create another vendor decoder.

Even `MATCHES_DECLARED_SCOPE` leaves chain applicability and issuer authenticity
unestablished, and correction authorization `NOT_GRANTED`. A missing instrument
identity stays unknown. A known differing identity, unit, range, reference or
interval produces `MISMATCH`. Neither the declaration nor observation is changed.

The same assessment can be retained through the CLI:

```powershell
python -m ciw.calibration_inspection certificate.xml --link-context context.json --output retained-inspection
```

`context.json` contains exactly `declaration`, `device`, `observation`, and `scope`
(which may be null). The file's exact bytes are retained alongside the source.
The embedded certificate must equal the supplied file bytes, not merely parse to
the same XML. The scope has no grant, approval or executable-expression fields.

## Existing history projections

`ciw.evidence_history` implements `ncp.retained-history-rules.v1` over the existing
Link journal and control checkpoint formats. Its JSON report includes source
hashes, rule version, per-rule `CONSISTENT` / `VIOLATED` / `UNKNOWN` outcomes and
counterexample IDs from the actual retained records. `NO_VIOLATION_FOUND` is a
bounded consistency result, not an authenticated or physically complete history.

```powershell
python -m ciw.evidence_history link-journal closed-journal.sqlite --output history.json
python -m ciw.evidence_history link-journal closed-journal.sqlite --claim-complete-stream --output completeness.json
python -m ciw.evidence_history control-checkpoints before.json after.json --output jobs.json
```

The Link reader uses the existing closed/checkpointed SQLite read-only snapshot
inspector. Original byte/index/configuration bindings must pass before temporal
checks. Observation ticks cannot move backwards within the same device/boot;
equal ticks across channels are allowed. A recorded `clock_reset` followed by
another observation in the same boot is a counterexample. A newly identified
boot permits a new tick domain. Missing ticks or absent reset records do not
establish a physical chronology. Overflow and sequence gaps are recorded and
contradict an explicit complete-stream assertion; even gap-free records cannot
prove acquisition completeness.

Control inspection accepts 1–64 operator-retained checkpoint snapshots in
caller-declared order, at most 8 MiB each and 32 MiB total. It verifies each
existing checkpoint seal, recomputes retained plan digests/identities, checks
compilation and experiment seals plus host-policy binding, and checks admitted
plan bindings, stable attempt/run identities, result/state consistency and immutable
terminal/unknown outcomes across snapshots. A single checkpoint cannot prove a
transition. Full plan recompilation and source/provider revalidation remain with
the original owner; content seals do not establish those checks or authenticate
an author. Queued/running snapshots cannot establish an actual interruption or
completion. The inspector never calls owner recovery or dispatch; the existing
ControlHost remains responsible for recovering unfinished work to an unknown or
retained outcome without automatic replay.

Neither record format contains a complete ordered grant-revocation/dispatch
history. That rule therefore reports `UNKNOWN`; a snapshot policy or a hash
cannot supply the missing facts. This module creates no event ledger and does
not claim that a `CONSISTENT` rule authenticates its author, installed hardware,
clock synchronization or certificate issuer.

## Verification

`tests/test_calibration_inspection.py` covers bounded XML failures, altered and
missing identities, unit/range/reference/time mismatches, exact decimal range
boundaries, signature non-authority, unchanged inputs and exact CLI retention.
`tests/test_evidence_history.py` uses real synthetic DeviceRuntime journals and
real ControlHost-produced checkpoints, injects tick/reset/overflow and rehashed
job/admission faults, and checks that inspection never resumes or rewrites them.
The synthetic DCC fixture intentionally covers only the declared inspection
subset; it is not asserted to be a fully XSD-valid or authentic DCC.
